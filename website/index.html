Assignment G3 prototype

Research that stays inside the lines

A multi-step agent that decomposes questions, gathers web evidence, stores it in bounded memory, compacts when needed, and answers with budgeted retrieval—so cost and context stay predictable.

Run a query CLI & API notes

Why this design

Client value is less “more text” and more governed research: predictable cost, bounded context, and traceability. The prototype makes budgets and retrieval explicit so you can see which evidence reached the final answer.

◎

Declared budgets

Caps on injected context and session memory are first-class. Optional USD ceilings stop sessions early when estimated spend crosses a limit.

↗

Traceable evidence

Structured output includes which memory chunks were selected for synthesis—so reviewers can connect behavior to governance, not guesswork.

◇

Built for ops

Same research policy runs in Python whether you trigger it from the CLI, FastAPI, or an n8n webhook—so constraints stay centralized.

How it works

Each complex question is split into sub-questions. For each one, the model uses tools (web_search, fetch_url), writes observations into episodic memory, optionally summarizes when the store grows too large, then packs the best-ranked chunks into a fixed budget for the final answer.

1

Decompose

The LLM breaks the user question into focused sub-questions so research stays scoped and repeatable.

2

Collect

Mistral tool calling drives search and page fetch loops per sub-question, with mock mode for offline demos.

3

Remember (bounded)

Observations land in an episodic buffer with token estimates; compaction merges older rows when limits hit.

4

Retrieve

BM25 ranks chunks; greedy packing fills max_context_tokens_per_llm_call before synthesis.

5

Answer

Final generation cites chunk labels and respects the injection cap—reducing attention dilution and runaway cost.

What ships (brief alignment)

The repo matches the G3 brief: Mistral + tools, explicit memory policy, and workflow hooks.

Brief item Implementation
LLM + tool use Mistral via mistralai, tool calling for web_search and fetch_url (research_agent/mistral_tooling.py)
Memory Episodic buffer, summarization cascade, BM25 + budgeted packing (research_agent/memory.py)
Constraints Self-defined caps in research_agent/config.py (context budget, session memory, optional USD)
Workflow n8n imports orchestration/n8n_g3_research.json → webhook → POST /research on FastAPI

    Honest trade-offs
    
        
    
          The system prefers operational clarity over embedding-heavy RAG for short, noisy web snippets. Summaries can drop
          rare details; BM25 is weaker on paraphrase than vectors—but budgets stay legible.
        
    
        
    
          
    
            Budgeted packing
            
    Upside: respects a hard injection cap. Downside: greedy packing is not globally optimal.
    
          
    
          
    
            BM25 retrieval
            
    Upside: local, cheap, predictable. Downside: synonyms and paraphrase can rank poorly vs embeddings.
    
          
    
          
    
            Summarization cascade
            
    Upside: long sessions stay bounded. Downside: compression can lose nuance if the model over-merges.
    
          
    
          
    
            Mock tools mode
            
    Upside: reproducible demos without credentials. Downside: not a substitute for live search quality.
